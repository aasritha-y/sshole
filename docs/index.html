*sshole

Why some Alpine Linux servers may let anyone log in to an account that is supposed to be locked, explained from the ground up.

OPENSSH · MUSL · NO PAM

In short

A security researcher has reported that on servers running Alpine Linux (and other systems built the same way), the SSH login service can be tricked into letting someone into an account that was deliberately locked, such as root. The trick is to type a password that is longer than 256 characters. Any such password works; it does not need to be the right one.

It happens because of how two pieces of software fit together: musl, the small system library Alpine is built on, and OpenSSH, the SSH server. The safety net that most other Linux systems have in between, called PAM, is missing on Alpine by default, so nothing catches the mistake.

If you run Alpine servers that accept SSH password logins, turning password login off closes the hole straight away.

PART 1

First: how a Linux server checks your password

A server never stores your actual password. It stores a scrambled version of it, called a hash, in a protected file named /etc/shadow. A hash looks like $6$abc$k2P9...: the $6$ says which scrambling method was used (SHA-512), abc is a random value called the salt, and the rest is the scrambled result.

When you log in, the server takes what you typed, scrambles it the same way with the same salt, and compares the two results. If they are identical, the password was right. The function that does the scrambling is called crypt().

Some accounts should never be logged into with a password at all, for example root on a cloud server where everyone is supposed to use SSH keys. For those, the hash is replaced with a single *. Since * is not a valid scrambled result of anything, no password can ever match it. The account is effectively locked for passwords, while SSH keys can still be used. This convention goes back to Unix in 1980.

PART 2

What musl is, and why Alpine uses it

Every Linux program relies on a C library (often called libc) for basic jobs like reading files, allocating memory and, here, scrambling passwords with crypt(). Most Linux distributions, such as Debian, Ubuntu and Fedora, use glibc, the large GNU C library.

musl is a different C library, designed to be small, simple and easy to audit. Alpine Linux uses musl instead of glibc, which is a big part of why Alpine is so tiny (a base Alpine image is a few megabytes). That small size makes Alpine extremely popular as the base for Docker containers, and it is also common on routers and embedded devices through OpenWrt, Buildroot and Yocto.

The detail that matters here: when musl's crypt() cannot do its job, it does not return "nothing" like the official standard describes. Since 2012 it returns the single character * instead, so that programs which forget to check for errors do not crash. And musl refuses to scramble passwords longer than 256 bytes (a protection against someone slowing the server down with huge passwords), which counts as a failure. So a password over 256 characters makes musl's crypt() hand back *.

PART 3

What PAM is

PAM stands for Pluggable Authentication Modules. It is a shared layer that sits between programs that need to log people in (SSH, the console login screen, sudo) and the actual checking of who someone is.

Without PAM, every program would need its own code for reading /etc/shadow, checking passwords and deciding whether an account is locked. With PAM, the program simply asks "is this the right password for this user?" and PAM answers, using whichever modules the administrator has configured. Those modules can check the local password file, a company directory such as LDAP, a one-time code app, and so on. Think of PAM as a building's central security desk: each door does not need its own guard, they all phone the desk.

On most Linux distributions, OpenSSH is built to use PAM. PAM's standard password module recognises that a * in the password file means "locked" and refuses straight away, without even trying to scramble the password. That is the safety net.

PART 4

Why Alpine is the system at risk

Alpine combines both conditions needed for the problem:

  1. It uses musl, so a password over 256 characters makes crypt() return *.
  2. Its standard OpenSSH server is built without PAM. Alpine keeps things minimal, and PAM support is not part of the default SSH server. So instead of asking PAM, OpenSSH checks the password itself: it calls crypt() and compares the result with what is stored in /etc/shadow.

Put those together and a locked account stores *, musl returns * for the over-long password, OpenSSH compares * with *, sees a match, and lets the person in.

A Debian or Ubuntu server does not have this problem, for two separate reasons: it uses glibc, whose crypt() does not return a bare *, and its SSH server goes through PAM, which rejects locked accounts before crypt() is ever called.

PART 5

The bug, step by step

1

An account is locked for passwords, so /etc/shadow stores just * for it.

2

An attacker connects over SSH and types a password longer than 256 characters.

3

Because there is no PAM, OpenSSH asks musl's crypt() to scramble that password.

4

musl refuses anything over 256 bytes, treats it as a failure, and returns *.

5

OpenSSH compares the returned * with the stored *. They are equal, so it decides the password was correct and logs the attacker in.

PART 6

Are you affected?

According to the write-up, a server is at risk only when all of these are true:

  • The SSH server runs on musl (Alpine, OpenWrt, Buildroot, Yocto, many Docker images built on Alpine).
  • OpenSSH is not using PAM (the Alpine default, or UsePAM set to no).
  • Password logins are allowed (the default unless someone turned them off).
  • At least one account has just * as its password, such as a key-only deploy user, an LDAP user, or root on Alpine.
  • Some other account on the server has a real password set.

The write-up highlights Alpine's official AWS and Azure images: their default alpine user is locked this way and can run admin commands without a password through doas (Alpine's equivalent of sudo), so getting into it amounts to full control of the server.

Reported as not affected

  • Debian, Ubuntu, Fedora and other glibc-based systems.
  • Any system where OpenSSH goes through PAM.
  • Dropbear, a different SSH server often used on small devices.
  • OpenBSD.
PART 7

What to do

  • Turn off password logins if you do not need them. Add a file /etc/ssh/sshd_config.d/00-no-passwords.conf containing PasswordAuthentication no, then restart SSH with rc-service sshd restart. This removes the hole regardless of version. Make sure your SSH key works first so you do not lock yourself out.
  • Update OpenSSH. The write-up says version 10.6p2 fixes it (apk upgrade openssh on Alpine). Confirm this against Alpine's and OpenSSH's own security advisories.
  • Check whether it was used against you. Search your SSH logs for Accepted password for on accounts that should only ever use keys, especially root and alpine.
  • Rebuild Docker images based on Alpine after the fix is available, since containers keep the version they were built with.
PART 8

What is confirmed and what is not

This page explains the issue as described in the public write-up at sshhole.com. The background facts (how password hashes work, what musl and PAM are, that Alpine uses musl) are well established. The vulnerability itself, the version that fixes it, and the researcher's testing (about 17,600 login attempts against differently built servers) have not been independently verified here. Check the linked sources and the official musl, OpenSSH and Alpine announcements before acting on the details.

TIMELINE

How it came about

No single change caused this. Each step below was reasonable on its own; the problem only appears when they meet.

WhenWhat happenedSource
1980 * means "locked". Early Unix marks accounts nobody should log into with a * instead of a password hash. 3BSD /etc/passwd
1997 crypt() should return nothing on failure. The Unix standard says crypt() returns NULL (an empty "no result") when it fails. Many programs never check for it and crash. Single UNIX Specification, crypt()
Aug 2012 musl returns * instead. To stop those crashes, musl makes a failed crypt() return *, which can never match a real hash. The same character already means "locked". musl commit b3c4cc12
Aug 2012 musl caps passwords at 256 bytes. SHA-512 scrambling gets slower with longer input, so musl refuses anything over 256 bytes. Refusing counts as a failure, so it returns *. musl commit 88bf5a8a
2016 OpenSSH starts hashing for every account. CVE-2016-6210: attackers could tell which usernames exist by timing failed logins. The fix makes OpenSSH always run crypt(), even for accounts it would otherwise reject quickly. The write-up dates the exposure from here. openssh-commits, July 2016
2019 to 2022 Alpine locks root with *. After CVE-2019-5021 (Alpine Docker images shipped with an empty root password), Alpine first locked root with !, which also blocked SSH keys without PAM. Alpine 3.16 switched to *, which keeps keys working and, per the write-up, made root reachable through this bug. alpine aports commit fbe926af
Nov 2026 Reported. The researcher built OpenSSH in every combination (glibc or musl, with or without PAM) and found only musl without PAM accepted logins it should have refused. sshhole.com
GLOSSARY
SSH
Secure Shell, the standard way to log into and control a server remotely. OpenSSH is the most widely used SSH server.
Hash
A one-way scrambled version of a password. The server stores this, never the password itself.
Salt
A random value mixed into each password before hashing, so two people with the same password get different hashes.
crypt()
The system function that turns a password and salt into a hash.
libc
The core C library every Linux program depends on. glibc and musl are two different ones.
musl
A small, simple C library used by Alpine Linux instead of glibc.
PAM
Pluggable Authentication Modules, the shared layer most Linux systems use to check logins on behalf of programs like SSH.
/etc/shadow
The protected file that stores each account's password hash, or * for accounts locked to passwords.
