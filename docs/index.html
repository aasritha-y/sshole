did you get hacked? check.

OpenSSH on musl Linux (Alpine, OpenWrt, Buildroot, Yocto, and many Docker images) is described as having a problem since 2016. Accounts that should never take a password (root, key-only deploy users, LDAP users, the default user on Alpine cloud images) are said to accept any password longer than 256 characters.

the sequence

1980

the first star

In old Unix the password hash sat in /etc/passwd, next to the username, in a world-readable file. A single * was put there for the daemon account, which nobody should log in as. A * is not a hash, so no password can match it. Unix still does this today.

3BSD, /etc/passwd, 1980 : source
1990s

how sshd checks your password

Today the hash lives in /etc/shadow and looks like $6$abc$k2P9.... The $6$ means SHA-512, abc is the salt, and the rest is the hash. You type a password, sshd hashes it with the same salt, and checks whether the result is identical. If the field is just *, there is nothing to match, so no password gets you in.

1990s

the fine print

If crypt() cannot do its job, it returns NULL. For example, the salt may ask for an algorithm the system does not have. Many programs never check for NULL. They compare whatever crypt() returns with the stored field and crash.

The Single UNIX Specification, crypt(), 1997 : source
2012

crypt stops saying NULL

musl (the C library under Alpine) decides crypt() will no longer return NULL. On failure it returns a single character that can never match a real hash, so programs see a wrong password instead of crashing. The character chosen was *, the same character used to mark locked accounts.

musl, b3c4cc12, aug 2012 : source
2012

three weeks later

musl adds SHA-512 crypt. It gets slower as the password gets longer, so a huge password could keep a server busy. musl caps input at 256 bytes and refuses anything longer. Past 256 bytes crypt() fails, and when it fails it returns *.

musl, 88bf5a8a, aug 29 2012 : source
2016

sshd borrows a salt

CVE-2016-6210. Asking sshd about a user that does not exist returned instantly, because there was nothing to hash. Real users took a few milliseconds longer, so timing revealed who exists. The fix: when there is no real hash, sshd hashes your password against another account's salt anyway, to spend the same time.

openssh-commits, jul 2016 : source
2019 to 2022

the fix for the fix

2019: Alpine Docker images had no root password at all (CVE-2019-5021). Alpine locked root with !, but without PAM that also blocks SSH keys, and cloud images log in with keys. 2022: Alpine 3.16 switched root to *. Still locked, and keys work again.

alpine aports, fbe926af, shipped in 3.16, 2022 : source
2016 to 2026

ten quiet years

Why did nobody notice? A fresh box with no passwords set is not affected. A * in shadow needs a wrong try first. OpenSSH is tested on OpenBSD and glibc, musl does not test sshd, and most distros go through PAM, which never calls crypt() for a *. As far as anyone knows, nobody noticed.

libc-alpha, debian #714219, 2013 : source
nov 2026

how it was found

The author built sshd many ways (glibc, musl, PAM, no PAM, shadow, no shadow) and sent about 17,600 unusual logins at each. Every build agreed on every login except musl without PAM.

summary of the public write-up; not independently verified

the chain, step by step

  1. Locked account stores * in /etc/shadow.
  2. You send a password longer than 256 bytes.
  3. musl's crypt() fails and returns *.
  4. sshd compares that * to the stored *.
  5. They match, so login is granted to a locked account.

are you affected?

  • sshd running on musl (Alpine, OpenWrt, Buildroot, Yocto)
  • not using PAM (Alpine's openssh-server does not by default, or UsePAM no)
  • password logins still on (the default)
  • an account with just * as its password (key-only users, LDAP users, root on Alpine)
  • some other account with a real password

If all of the above are true, a * account is said to accept any password between 257 and 1024 characters. On Alpine's official AWS and Azure images that is the default alpine user, which has passwordless doas, so it is effectively root.

not affected

  • Debian, Ubuntu, Fedora, anything with glibc
  • any distro going through PAM
  • Dropbear
  • OpenBSD

what now

  • Upgrade OpenSSH to 10.6p2 or later (version as stated by the write-up; confirm against the OpenSSH and Alpine advisories).
  • Restart sshd after upgrading (rc-service sshd restart on Alpine).
  • If you cannot upgrade: set PasswordAuthentication no and restart sshd.
  • Check logs for Accepted password for on accounts that should be locked.
